# Retrieval Evaluation Methodology

## Relevance definition and why
No human-annotated relevance judgments exist for this dataset. Rather than
skip evaluation or invent labels, we use **issue_type match** as a proxy:
a retrieved historical incident is "relevant" to a query if it shares the
same issue_type as the category the query was designed around.

## Why this is a reasonable proxy, and its limits
- `issue_type` is a real, meaningful category boundary in this dataset (Stage 5 EDA:
  8 well-balanced classes), so a same-category match is a defensible relevance signal.
- It is coarse: two incidents can share an issue_type but describe very different
  specific problems, or (more rarely) different issue_types could plausibly be
  considered related by a human expert. This metric cannot capture that nuance.
- With ~12,500 incidents per issue_type class in a 100K corpus, Recall@K in
  the traditional sense (retrieved relevant / total relevant in corpus) is not
  meaningful — there are thousands of "relevant" incidents by this definition.
  We report **Precision@K** and **Hit@K** (did a relevant result appear at all
  in the top K) instead, which are meaningful at this corpus scale.

## Controlled test set
10 deliberately designed cases (`data/test/controlled_eval_set.py`) covering:
near-identical, paraphrase, related-but-different, unrelated, duplicate, short,
noisy, missing-information, empty, and unseen-vocabulary queries — per the
project's dataset strategy. Real Precision@1/3/5 and per-case results are in
`reports/retrieval_evaluation.md`, generated by actually running
`scripts/evaluate_retrieval.py` — not estimated here in advance.

7 of 7 categorizable test cases hit at K=1 except T6 (short) and T7 (noisy),
which both failed completely — 0 of 5 results matched the expected
`account_access` category.

### Root cause (diagnosed, not assumed)
This is a genuine, explainable tokenization mismatch, not a general failure
of short/noisy text handling:

- `account_access` tickets in this dataset phrase login issues as **"log in"**
  (two words) — e.g. "the system says my password is incorrect" style tickets.
- Stage 6's preprocessing removes "in" as a stopword, leaving the surviving
  token as **"log"**, not "login".
- Test queries T6/T7 used **"login"** as one word (a natural way to phrase it),
  which is a different token from "log" — TF-IDF has no way to know these
  refer to the same concept.
- The one-word "login" instead matched unrelated `how_to` tickets that
  literally contain the token "login" (e.g., "login auth" phrasing), which is
  why the wrong category was retrieved instead of just a worse rank.

### Implication
This is a genuine limitation of naive stopword removal combined with
phrasal-verb vocabulary ("log in" as two words vs. "login" as one) — not a
flaw specific to short or noisy text. A user typing the very common phrasing
"login" would get zero relevant results for account-access issues despite
the corpus containing thousands of related incidents, phrased with a space.

### Possible future fix (not applied in this stage)
A normalization step mapping "log in" <-> "login" before tokenization (e.g.
a targeted regex or a domain synonym list) would likely resolve this. Left
as a documented finding and candidate improvement rather than reopening
Stage 6's already-committed pipeline mid-evaluation — a change like this
should be made deliberately, with its own before/after measurement, not
patched reactively into this stage.
